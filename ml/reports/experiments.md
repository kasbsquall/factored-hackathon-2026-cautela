# Experiment tracking: the runs behind the committed ML results

Generated by `ml/experiments_report.py` from `ml/reports/experiments_runs.json` (a snapshot of the local MLflow
store in `mlruns/`, which is git-ignored) and from the committed report files. Do not edit by hand. Regenerate with
`uv run python -m ml.experiments_report`; browse the local store with
`uv run mlflow ui --backend-store-uri sqlite:///mlruns/mlflow.db`. Run ids are shortened to 8 characters; the full
ids, every param and every logged metric are in `experiments_runs.json`. Dates are UTC. Offline evaluation on
generated scenarios over organizer transactions, not production results.

A run is linked to a report file only when its logged metrics equal the numbers in that file: the headline metrics
of each system for evaluate runs, every validation metric for train runs. When several runs match, the one whose
logged latency also matches is the run that wrote the file; the others are identical re-runs.

## Model selection, with the file behind each claim

### 1. Pointwise ranker (`fitted.json`)

7 candidates were fitted on 2259 train cases (7767 candidate rows) and scored on 754 val cases. The rule in `ml/train.py` is highest val MRR on match cases, then lowest val log loss; every candidate reached val MRR 1.0, so the tie-break on val log loss picked `hgb_d6_lr0.1` (val log loss 0.011).

### 3. Disposition model family

* `fitted.json`: val log loss `multinomial_logreg_C1` 0.0481, `hgb_d3` 0.0541; `multinomial_logreg_C1` is lower than the next family by 0.0060; selected `multinomial_logreg_C1`.
* `previous/fitted.json`: val log loss `multinomial_logreg_C1` 0.0777, `hgb_d3` 0.0757; `hgb_d3` is lower than the next family by 0.0020; selected `hgb_d3`.

The family is chosen on val log loss alone. The two runs disagree on which family has the lower val log loss, and the margins above are small, so the family choice rests on a narrow val difference; either family is defensible.

### 4. Why the LLM ranker does not decide (`results_llm.json`)

On the same 1107 test cases, run 1 of `gpt-6-luna` with prompt `rank_v1` acts in 259, asks in 617 and hands off 231. Top-1 on match is 97.2% against 99.1% (`rules_tuned`), 99.9% (`learned_ranker_disposition`); correct decisions 54.0% against 86.8%, 93.9%; unsafe 12 against 21, 3.

| paired, LLM run 1 minus | correct decisions | unsafe | safe automated resolution |
|---|---|---|---|
| `rules_tuned` | -32.8 [-36.4, -29.3] | -0.8 [-1.7, +0.1] | -28.0 [-31.2, -24.8] |
| `learned_ranker_disposition` | -39.8 [-43.5, -36.1] | +0.8 [+0.2, +1.6] | -34.6 [-38.1, -31.3] |

Decision and top charge repeat in all 3 runs for 838 of 1107 cases; spend USD 0.37056. The decision stays with `learned_ranker_disposition`.

### 5. Why gpt-6-luna for extraction (`probe/*.json`)

The probes ran prompt `rank_v1` on the same 50 val cases through the provider-agnostic port in `agent/llm` (masking, JSON schema check, token and cost accounting), the port the agent also uses for extraction. Highest top-1 on match: `gpt-6-luna`. Lowest median top score on no_match cases, that is, least confident about charges that are not there: `gpt-6-luna`. Cheapest paid model: `gpt-6-luna`. The probe table above has the numbers.

Limit of this evidence: the probes score the ranking prompt. No committed file compares models on the extraction prompt itself. `agent/README.md` records a separate local run of `qwen2.5:7b-instruct` on the demo scenarios (section "Local model run") and the reason `LLM_REASONING_EFFORT` is `none` for extraction (reasoning tokens bill as output).
